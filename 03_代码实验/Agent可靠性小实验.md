# Agent 可靠性小实验：让订单真的改对

**先抓住一句话：Agent 说“我办好了”，和系统里“事情真的办好了”，是两回事。**

这里用一个故事贯穿八个实验：Alice 有一张订单，当前数量为 1、版本为 1。她希望把数量改成 2；环境只允许她修改自己的这张订单，数量最多为 3。工具可能在提交前或提交后丢失响应。

全部操作都发生在程序内存里，运行结束即消失。**不访问网络、不调用模型、不改真实订单，程序本身只打印 JSON。** 对照项是我们刻意写出的薄弱规则，不代表某个大模型的能力，也不会产生“模型成功率”。

## 先看八个实验究竟教什么

| 故障或对照 | 容易犯的错 | 要保留的工程行为 |
|---|---|---|
| 只生成改单计划 | 已有动作 JSON，就宣布完成 | 计划与执行分开；没有回执、终态就没有成功证据 |
| 参数、权限或版本不对 | JSON 能解析，就执行 | 数量类型与范围、用户授权、订单版本都要检查 |
| 工具超时 | 把超时当作确定失败 | 超时只说明没有拿到响应；用原操作编号查提交结果 |
| 连回执也查不清 | 换一个编号再提交 | 保留“未知”和原命令；恢复时沿用原编号与原参数 |
| 聊天被压缩 | 摘要只剩“把数量改成 4” | 数量上限、用户、订单、版本、操作编号放入独立状态 |
| 检索出记忆 | 只要相似就全塞进上下文 | 按用户隔离，检查有效期；记忆内容不能授予权限 |
| 调用预算耗尽 | 一直重试，或声称没有执行 | 停止调用；区分“还没发出”和“发出后结果未知” |
| 评测 Agent | 检查回答里有没有“成功” | 检查真实订单、对应回执和修改次数 |

结合 A03–A07、A09–A11、A13 阅读。KD22–KD23 讨论 Agent 蒸馏与评测时，也可以把这里的故障场景作为需要覆盖的轨迹类型。

## 第一课：为什么需要“订单版本”

你读到版本 1，准备修改；另一个人已经把订单改成版本 2。此时继续按旧信息操作，可能覆盖对方的修改。

所以命令除了写“改成 2”，还要带上“我依据的是版本 1”。服务端发现版本不一致，就拒绝这次修改。接下来应重新读取状态、重新判断用户目标，而不是机械重试旧命令。

这里的权限由模拟环境预先配置。即使 Agent 在自己的上下文里写“数量上限是 99”，服务端仍会按真实授权上限 3 拦截。

## 第二课：超时为什么有三种结果

想象你提交表单，页面一直转圈：服务器可能还没收到，也可能已经处理完，只是回信丢了。

- **查到提交回执：**本次操作已完成，直接使用回执。
- **权威确认尚未提交：**允许按原操作编号、原参数重试。
- **回执查询也不可用：**保留“未知”，停止盲目提交，等待后续恢复。

操作编号相当于这一次改单的“取件码”。同编号、同命令再次到达时，服务端返回原回执；同编号换了数量，会被拒绝。这样恢复原操作时不会误变成第二次操作。

**模拟边界：**本实验假设单进程原子提交，而且可用的回执查询是强一致的。在真实系统中，如果查询有延迟，“没查到”可能仍是未知。生产系统还需要持久化操作记录、权限校验、幂等记录保留期，以及适合具体业务的一致性协议。这个小实验没有实现分布式事务。

## 第三课：上下文压缩、记忆、预算各管什么

**压缩聊天**负责删掉闲聊与冗长描述。任务数量上限、操作编号等字段独立保存，压缩函数没有权限改它们。本实验验证这种状态组织方式，不是在评测某个模型的摘要质量。

**检索记忆**负责返回当前用户尚未过期的信息。实验采用外部给定的整数时间，便于复现到期边界；到期时刻就算失效。通过过滤不代表内容已被验证，所以回忆里的“我有权限”仍不能修改服务端授权。

**预算**负责决定还可以调用几次工具。实验只计算调用次数，没有估算 token、金钱和真实耗时。预算用完时，如果上一次调用可能已提交，状态必须留在“未知”，不能把它改写成确定失败。

## 怎样运行

在本目录打开终端，执行：

~~~powershell
python agent_reliability_examples.py
python -m unittest test_agent_reliability.py -v
~~~

第一条会输出包含八个场景的 JSON。每个场景都有 `baseline` 和 `guarded`：前者记录薄弱规则的问题，后者记录模拟环境中检查得到的行为。第二条运行 8 项故障与对照验证。

重点观察这些结果：

- 只做计划：`actual_success` 为 `false`，写入次数为 `0`。
- 提交前超时与提交后超时：恢复后都只有 `1` 次写入，工具调用次数分别为 `3` 和 `2`。
- 回执不可见：第一次结果是 `unknown`；恢复可见后用原操作编号重放，仍只有 `1` 次写入。
- 上下文压缩：目标数量 `4` 仍被上限 `3` 拦截，工具调用次数为 `0`。
- 提交后只有一次调用预算：实际已写入，但对调用方只能报告 `unknown`。
- 回答声称成功却没有执行：终态评测为 `false`。

## 面试时怎样讲这个项目

可以这样概括：

> 我搭了一个可重置的订单模拟环境，给相同任务注入超时、旧版本、上下文压缩和记忆污染等故障。系统把计划、工具回执和真实状态分开记录；结果不明时保留原操作编号，受预算约束地恢复；最后根据环境终态评测。现阶段验证的是系统规则，尚未证明任何模型的能力提升。

下一步若接入真实模型，可以比较“只有提示词”和“提示词加这些系统约束”两个版本，保持工具权限、任务集、预算一致，统计任务完成、错误操作、未知结果处理与调用成本。训练集和测试集应按任务模板及故障组合隔离。**只有实际运行这组评测后，才能报告模型或 Agent 的成功率。**
