# 12 推理、显存与服务性能

先区分读题与写答案（I01），再理解保存历史笔记（I02）和数缓存里的数字（I03）。显存、速度、等待与成本分别计算，最后再看具体加速算法。

<a id="I01"></a>
## I01｜Prefill 和 Decode 为什么性能特征不同？（P0）


### 先读完题目，再一个字一个字作答

Prefill 是处理已有输入、建立初始计算结果；decode 是在此基础上逐步生成新 token。前者一次有很多已知位置可计算，后者不断依赖刚生成的内容。

因此二者可能受不同瓶颈限制。输入很长时首字等待长；输出很长时，后续逐步生成的总时间也会大。

**直答：** Prefill 处理已有上下文，decode 逐步生成新内容；优化时分别看输入处理和每步生成的计算与访存。

### 进一步：公式、边界与追问

**本章进阶约定与范围：**

定位：算法岗需要能估算和定位瓶颈；不要求把所有 kernel 实现背下来。数字为教学估算，GB=10^9 字节，GiB=2^30 字节。

**技术表述：** Prefill 一次处理已知输入的多个 token；decode 每次为各请求生成少量新 token，并读取已有 KV。

**展开：** Prefill 较易形成大的矩阵乘；小 batch decode 常受权重/KV 访存限制。实际瓶颈随 batch、长度、硬件、量化和注意力实现变化，不能绝对分类。

**追问：为什么首字快但后续慢？** 输入短可降低 prefill，但长历史 KV 读写、batch 调度或网络输出会影响 decode。

**易错：** tokens/s 需说明是输入、输出、单请求还是全服务聚合。依据：S34。

<a id="I02"></a>
## I02｜KV cache 存什么，为什么不缓存 Q？（P0）


### 已读过的前文，不必每次重新做笔记

每生成一个新 token，都要参考历史内容。KV cache 保存历史位置算出的 K 和 V，让后续步骤可以直接使用，减少重复计算。

新一步主要使用新位置的 Q 去查询历史 K/V；旧位置的 Q 已完成对应输出计算，通常无需为未来步骤继续保留。

**直答：** KV cache 保存历史键和值，供新位置查询；它用显存换取少做重复计算，历史 Q 通常不参与新的查询输出。

### 进一步：公式、边界与追问

**技术表述：** 存每层历史位置的 K/V，供未来 token 查询；旧位置的 Q 通常不会再用于计算新位置的输出。

**展开：** 自回归推理中，新 token 的 Q 与所有可见历史 K 匹配，再聚合 V。缓存避免重复计算历史 token 的 K/V，但仍要读取和使用历史。

**追问：KV cache 会降低模型参数量吗？** 不会，它是运行时状态，反而占额外显存，以换取计算复用。

**易错：** 不要将 KV cache 说成缓存最终答案。依据：S34。

<a id="I03"></a>
## I03｜KV cache 显存如何手算？（P0）


### 数一数缓存里到底放了多少个数字

先算一层、一个 token：有 K 和 V 两份，每份包含若干 K/V 头，每头有一定维度。再乘历史 token 数、层数、并行请求数，得到数字总个数；最后乘每个数字占的字节。

例如 32 层、8 个 K/V 头、每头 128 维、8192 个 token、一个请求、每数 2 字节：2×32×8×128×8192×2=1 GiB。

**直答：** KV 显存按“保存两份什么形状的张量”逐维相乘；明确层数、K/V 头数、维度、长度、批量和精度，再检查特殊结构与额外开销。

### 进一步：公式、边界与追问

常见标准 attention、K/V head dim 相同，忽略分页碎片与额外元数据：

$$M_{\rm KV}=2\cdot L_{\rm layers}\cdot B\cdot T\cdot H_{\rm kv}\cdot d_h\cdot b.$$

**技术表述：** 2 表示 K/V，b 是每元素字节数，T 是每请求当前缓存长度；变长请求用各 T 之和替代 B·T。

**算例：** 32 层、batch=1、T=8192、8 个 KV 头、head dim=128、BF16 2 字节，约 1 GiB；若 32 个 KV 头，约 4 GiB。

**追问：MLA/混合注意力适用吗？** 需按实际缓存表示重算，不能直接套这个标准式。

**易错：** 参数精度与 KV 精度可能不同。依据：S03、S34。

<a id="I04"></a>
## I04｜模型权重、训练与推理显存怎么估算？（P0）


### 放教材的空间，和做作业的草稿空间

推理要放模型权重，还要放缓存、中间结果和服务需要的空间；训练还可能保存梯度、优化器状态以及反向传播要用的中间信息。

所以“70 亿参数×每参数 2 字节”只估算了某种精度下的权重，不是训练或服务的全部显存。

**直答：** 按权重、缓存、中间激活、梯度和优化器状态分项估算，结合运行方式确定哪些存在，避免把参数存储当成总显存。

### 进一步：公式、边界与追问

**技术表述：** 推理看权重+KV+激活/缓冲；训练另加梯度、优化器状态与保存激活，是否有主权重副本依实现。

**展开：** 7B 参数 BF16 裸权重约 14GB；4bit 裸权重约 3.5GB，但都不是实际显存需求。典型混合精度 Adam 配置若含 BF16 权重/梯度、FP32 主权重和两个 FP32 动量，参数相关状态约 16 字节/参数。

**追问：为什么估计放得下却 OOM？** 未计 KV、临时 workspace、碎片、并行通信缓存或长输入峰值。

**易错：** 16 字节不是所有训练框架固定开销，参数分片与优化器实现会改变它。依据：S35。

<a id="I05"></a>
## I05｜PagedAttention 解决什么问题？（P0）


### 给每位客人预留整栋房子，容易浪费空间

不同请求的回答长度事先不确定。如果为每个请求连续预留很大缓存，容易产生空闲和碎片。PagedAttention 使用分块管理与映射，按需组织 K/V 存储。

它重点解决存储安排和共享，不是靠改变答案质量来换速度。

**直答：** PagedAttention 用分页式管理改善 KV cache 分配和利用率，减少连续预留带来的浪费，并支持相应共享。

### 进一步：公式、边界与追问

**技术表述：** 把 KV cache 按块分配并通过映射访问，减少连续大块预留带来的碎片与冗余。

**展开：** 每个请求的逻辑 token 序列不必对应连续物理内存；动态增长与共享更灵活。仍有块内尾部空间和元数据，不能宣称绝对零浪费。

**追问：它是稀疏注意力吗？** 主要是缓存组织与访问方法，不意味着只关注少数 token。

**易错：** 更省缓存可支持更多并发，但具体吞吐收益取决于 workload。依据：S34。

<a id="I06"></a>
## I06｜连续批处理与传统 batching 差别？（P0）


### 做完的人先离桌，新人马上补位

传统批处理可能让一组请求一起进、等全部完成再换下一组。有人回答两句话就结束，却要等其他人写长文。

连续批处理可以在运行过程中移出完成请求、加入新请求，让设备更持续地工作，但调度和缓存管理也更复杂。

**直答：** 连续批处理动态补充活跃请求，提高不同输出长度下的利用率；还要检查单个用户等待和服务公平性。

### 进一步：公式、边界与追问

**技术表述：** 连续批处理可在生成过程中让完成请求退出、新请求进入，提高不同长度请求混合时的利用率。

**展开：** 调度要平衡公平性、尾延迟、总吞吐与 KV 容量；大批量不必然让单请求更快。长 prefill 可能阻塞其他 decode，chunked prefill 是一种缓解思路。

**追问：为什么 GPU 利用率高但用户体验差？** 排队和长尾可能很高。必须看请求到达时间与端到端 SLO。

**易错：** 静态 batch 的最优吞吐不能直接代表线上负载。

<a id="I07"></a>
## I07｜Prefix caching 什么时候有效，何时失效？（P0）


### 大家读同一份开场材料，可以共用已做好的前半段计算

很多请求共享完全相同的系统提示或长文档前缀，prefix caching 可以复用这段的缓存，减少重复 prefill。

关键是模型实际看到的 token 前缀一致，而不只是两段文字“意思一样”。模型或缓存条件变化也会影响复用。

**直答：** 前缀缓存复用兼容条件下相同 token 前缀的计算；命中率取决于请求结构、版本和缓存策略。

### 进一步：公式、边界与追问

**技术表述：** 相同模型条件下，共享完全匹配的前缀可复用 KV，减少重复 prefill；不直接减少后续生成所需的 decode。

**展开：** 公共系统提示、固定文档前缀、多轮公共历史有机会命中。前缀前面插入随机时间戳或改变模板，会影响匹配；模型、adapter、位置与缓存实现也需兼容。

**追问：只要包含相同段落就能缓存命中？** 普通前缀缓存通常还依赖之前所有前缀内容，不能把任意相同中间片段视为独立可复用。

**易错：** 多租户复用需按系统边界保证隔离与正确性。依据：S50。

## I08｜Speculative decoding 为什么能保持分布？（P1）


### 小助手先起草，大模型按规则验收

小模型快速猜几个 token，大模型一次检查这些候选；接受多少、拒绝后怎样重采样，都有严格规则。符合对应条件时，可以保持目标大模型的采样分布。

它不是把小模型的答案未经验证直接交出去。草稿经常不被接受时，也可能没节省多少时间。

**直答：** 推测解码用廉价草稿减少昂贵串行生成步骤，靠正确的验收与重采样保持目标分布，收益取决于接受率和实现成本。

### 进一步：公式、边界与追问

**技术表述：** 草稿模型先提议多个 token，目标模型并行验证；使用正确接受与残差采样规则，可保持目标采样分布。

**展开：** 单步在草稿分布 q、目标 p 下，对提议 token 的接受概率为 min(1,p/q)；拒绝后从规范化的 (p−q)_+ 残差分布采样。精确性依完整算法与实现假设，不是任意“草稿+检查”都成立。

**追问：加速来自哪里？** 目标模型并行验证一段有机会比逐个 decode 更高效；草稿成本、接受率和硬件决定收益。

**易错：** 不承诺所有任务固定倍数提速。依据：S36。

<a id="I09"></a>
## I09｜Temperature、top-k、top-p 怎么选？（P0）


### 调整概率，再决定从哪些候选里抽

温度调概率分布的尖锐程度；top-k 只保留概率最高的 k 个候选；top-p 保留累计概率达到某阈值的一组高概率候选。

例如 k 固定为 10，无论模型多确定都按这个数量限制；top-p 的候选数会随当前概率分布变化。

**直答：** 三者分别改变概率尺度或截取候选集合；选择时联合考虑任务正确性、重复、多样性与可复现设置。

### 进一步：公式、边界与追问

**技术表述：** 温度重塑分布，top-k 限制候选数量，top-p 按累计概率质量截取候选集合，再重新归一化采样。

**展开：** 确定性评测可用 greedy 作为基线；推理覆盖实验应记录温度、top-p、候选数、最大长度。代码或结构化输出还要看格式约束。

**追问：top-p 会固定保留多少 token？** 不会，取决于当前分布尖锐程度。

**易错：** temperature=0 常是接口里的 greedy 约定，不是在数学式里直接除零。

<a id="I10"></a>
## I10｜TTFT、TPOT、吞吐与 p95 如何解释？（P0）


### 用户既在乎多久开始，也在乎后面写得多快

TTFT 是等到第一个 token 的时间；TPOT 描述后续每个 token 的平均时间；吞吐是系统单位时间完成多少工作。

p95 则关注较慢用户：约 95% 的观测值不超过这个数。平均很快，仍可能有少部分用户等得很久。

**直答：** 首字等待、后续生成速度、整体吞吐和尾部延迟是不同体验与效率指标，要分开报告。

### 进一步：公式、边界与追问

**技术表述：** TTFT 是首 token 等待，TPOT 表示后续 token 的平均生成时间，吞吐是单位时间总产出，p95 描述尾部体验。

**展开：** 记录计时边界：客户端排队、服务排队、prefill、decode、网络是否都包括。TTFT 低但输出慢，长答案仍会很慢。

**追问：怎么做负载测试？** 用真实输入/输出长度分布、到达率与并发，分别报告稳定负载和接近饱和时的延迟、错误与内存。

**易错：** 不能用平均延迟掩盖少量严重超时。

## I11｜吞吐提高后为什么总成本可能更高？（P1）


### 厨房每分钟出菜更多，不代表每单更便宜

为了提高吞吐增加更多 GPU，总费用可能涨得更快；允许回答更长也会增加 token 量，却不一定提高任务价值。

应同时看每个有效任务的成本、失败重试、设备空闲和用户等待，而不只看 tokens/s。

**直答：** 吞吐描述处理速率，成本还取决于资源、输出长度、利用率和成功任务数；效率提升必须按完整业务单位核算。

### 进一步：公式、边界与追问

**技术表述：** 可能模型生成更长、重试更多、批量等待更久，或额外调用了评审/检索/草稿模型。

**展开：** 成本应按成功任务或满足质量约束的请求计，而非只按输出 token。RAG 的检索与索引，Agent 的工具环境，RL 的验证器都要计入。

**追问：怎么展示方案取舍？** 画成功率—成本、吞吐—p95 等曲线，给出业务约束下的候选点。

**易错：** 单 kernel benchmark 的快不能证明端到端服务快。

<a id="I12"></a>
## I12｜性能问题应该怎样定位？（P0）


### 慢的是排队、读题、写答案，还是调用外部工具？

把总耗时分段记录，先看哪个阶段最慢，再观察计算设备、显存、网络和并发。若主要时间花在外部查询，优化 attention 未必有明显帮助。

每次改动后用相同请求分布重测，才能判断改善发生在哪里。

**直答：** 先分解时间与资源瓶颈，再选择优化点；用一致工作负载验证端到端收益。

### 进一步：公式、边界与追问

**技术表述：** 先分排队、模型计算、访存、检索、工具与网络，再针对主导瓶颈优化。

**展开：** 固定输入长度与输出长度测微基线；再逐步加入真实并发、长输入和工具。核查缓存命中、KV 占用、实际 batch、重试与冷启动。

**追问：先换更强 GPU 行吗？** 如果瓶颈在数据库或队列，收益有限；先量化耗时占比。

**易错：** 并发参数增大导致 OOM、排队和重试后，吞吐可能反而下降。
