# 11 Agent、工具、记忆与可靠性

**进阶入口：**第 20 章 AG01—AG36 已补齐工具协议、程序化调用、上下文、技能与记忆、长期任务、Agent 训练及 2026 评测。阅读器“Agent 50 题”将两章连成一条路线。

把 Agent 想成能使用工具的办事助手。先读 A01，再沿“状态—调用—结果—恢复”理解可靠性。重点是事情实际有没有办成，而不只是回答是否流畅。

<a id="A01"></a>
## A01｜Workflow 和 Agent 的区别是什么？（P0）


### 按固定菜谱做，还是根据现场情况决定下一步

Workflow 的主要步骤和分支由人预先规定；Agent 在给定目标与权限内，可以依据当前结果选择下一步工具或行动。

比如固定“查询—汇总—回复”和“先查缺什么信息，再决定补查或澄清”有所不同。自主选择更多，也增加失败组合和评测难度。

**直答：** 区别主要在执行过程由谁决定、能调整到什么程度；能用固定流程可靠完成的任务，不一定需要更高自主性。

### 进一步：公式、边界与追问

**本章进阶约定与范围：**

定位：把 LangGraph 项目从“流程编排”讲成可验证的决策系统。本章框架无关；具体 API 与默认行为以固定软件版本为准。

**技术表述：** Workflow 的主要执行路径由开发者预先规定；Agent 让模型在一定范围内选择下一步行动、工具和停止时机。

**展开：** 两者可混合：高风险业务流程保持明确约束，知识检索和诊断步骤允许灵活决策。选择自由度应对应真实任务需求与评测能力。

**追问：所有任务都值得 Agent 化吗？** 固定结构查询、简单分类可能用程序更可靠、更便宜；先建立规则或固定流程基线。

**易错：** 循环调用 LLM 不自动产生有效规划。

<a id="A02"></a>
## A02｜ReAct 为什么把推理和动作交替？（P0）


### 先行动获得新信息，再更新判断

查航班前只能猜有哪些选项；调用查询工具后，才知道实际时间和余票。ReAct 把思考、动作和观察交替起来，让下一步根据新信息调整。

若工具报错，也应把报错当作当前事实处理，不能继续假设查询成功。

**直答：** ReAct 通过推理—行动—观察循环，让规划与外部反馈相互更新，避免一开始就凭不完整信息定死全部步骤。

### 进一步：公式、边界与追问

**技术表述：** 让模型利用行动获得的新观察更新决策，减少只凭内部知识规划到底的错误。

**展开：** 模型提出下一动作，环境返回观察，再决定下一步。真正的增益来自外部信息和可纠错反馈，不是输出“Thought/Action”格式本身。

**追问：为什么不能一次计划全部工具调用？** 动态任务中后续参数可能依赖查询结果；但彼此独立的只读查询可并行。

**易错：** 文本写“已完成操作”不证明工具真的执行。依据：S30。

<a id="A03"></a>
## A03｜工具调用的 JSON 正确就算成功吗？（P0）


### 表格填得合规，不代表事情办对了

工具调用的 JSON 格式正确，只说明系统能读懂字段；航班日期填错、金额单位弄错、对象不对，仍会执行错误。

还要检查请求是否有授权、参数语义是否正确、工具是否成功，以及最终业务状态有没有变化到目标。

**直答：** 工具调用要依次验证格式、参数含义、权限、执行结果和最终状态；格式通过只是第一关。

### 进一步：公式、边界与追问

**技术表述：** 还要验证工具选择、参数语义、权限、执行结果和业务终态。

**展开：** schema 只约束形状，不保证订单 ID 存在、日期有效、金额单位正确或动作获授权。执行器应校验类型、枚举、范围、关系约束和调用上下文。

**追问：结构化输出为什么仍会失败？** 它可能生成格式合法但含义错误的参数。需要错误反馈与修正，而非无限重复。

**易错：** 不要把 tool call parse rate 叫 task success rate。

<a id="A04"></a>
## A04｜Agent 的状态应该记录什么？（P0）


### 办事过程中，要有一张可靠进度单

记录用户目标、已经确认的条件、查到的事实、工具结果、待解决问题和已经执行的动作。这样重试时才能知道从哪里继续。

尤其要把“打算退票”“正在请求退票”“已经退票成功”分开，否则模型的一句话可能被误当成已发生的事实。

**直答：** 状态应区分计划、证据、待办和已完成动作，并保留来源与执行标识，支持检查、恢复和结束判断。

### 进一步：公式、边界与追问

**技术表述：** 用户目标、已知事实与来源、计划状态、工具输入输出、约束、错误、待解决问题和终态证据。

**展开：** 状态应可序列化与恢复；大型文档可保存引用而非全部复制。工具副作用与会话文字分开记，避免模型压缩摘要时丢掉已经提交的操作。

**追问：为什么记录版本？** 同样问题在不同模型、索引、工具和政策版本下行为可能不同，回放需要这些信息。

**易错：** 一段自然语言总结通常不足以承担事务状态。

<a id="A05"></a>
## A05｜工具超时与失败如何恢复？（P0）


### 没收到回执，不等于事情没办成

退款请求发出后超时，可能根本没执行，也可能钱已退、只是回执丢了。立即重新退款，可能重复操作。

可靠恢复先用请求标识查询状态，再决定继续等待或安全重试。不同错误需要不同处理。

**直答：** 超时后先判断执行状态是否未知，查询并核对业务结果；涉及写入时不能把所有失败都当作可直接重试。

### 进一步：公式、边界与追问

**技术表述：** 先区分临时失败、参数错误、权限问题与执行状态未知，再选重试、修正、替代或升级处理。

**展开：** 只读请求可采用有上限退避；写入请求超时后先查状态，再决定是否重试。记录尝试次数、错误类型和剩余预算。

**追问：为什么执行状态未知最麻烦？** 请求可能已成功但响应丢失，直接重试可能重复提交。使用幂等键或业务唯一标识可减少重复副作用。

**易错：** 模型生成“重试一下”不是可靠重试策略。

<a id="A06"></a>
## A06｜幂等、事务与回滚为什么是 Agent 面试题？（P0）


### 同一张单据提交两次，应只办一次

幂等的意思是同一操作重复提交，结果不会重复叠加，比如同一退款单不会退两遍。事务要求一组操作按约定整体完成或处理失败；回滚尝试撤销已经发生的改变。

并非所有现实动作都能撤销。因此设计工具时，要把确认、重复请求和补偿处理考虑进去。

**直答：** Agent 会重试也会中断，必须依靠幂等、事务或补偿规则控制重复与半完成状态，不能只靠模型记住“别重复”。

### 进一步：公式、边界与追问

**技术表述：** Agent 能修改外部状态后，可靠性必须满足业务系统的基本一致性要求。

**展开：** 幂等让同一逻辑请求重复执行不产生额外副作用；事务使相关更新按一致规则提交；无法原地回滚的动作需补偿流程。关键状态检查应由程序执行。

**追问：多工具操作如何保证原子性？** 跨系统通常难有单数据库事务，可用状态机、步骤记录和补偿，并说明不可逆步骤边界。

**易错：** 在提示词中要求“不要重复”不能替代幂等实现。

<a id="A07"></a>
## A07｜Agent 任务成功率怎么定义？（P0）


### 说“已经完成”和真的完成，是两个分数

用户要求改到明天的航班，助手回复“已改签”，但系统仍是今天的机票，任务就没成功。

评价应检查预订记录、日期、费用和必要约束，而不只是最后一句话听起来是否正确。

**直答：** 用可核验的最终业务状态和约束定义成功，把对话质量与任务实际完成分别评分。

### 进一步：公式、边界与追问

**技术表述：** 核验最终环境是否达到目标，且过程未违反关键策略；不能只看最终回复。

**展开：** 退票任务需核对订单状态、退款额、权限与必要确认。即使目标终态正确，越权查询或违反业务规则也应单独记风险。

**追问：用户模拟器可靠吗？** 它会引入行为偏差；固定版本、场景和随机性，并辅以人工回放或真实匿名案例。

**易错：** 把“我已为您退票”当成功标签，会奖励虚假完成。依据：S31。

<a id="A08"></a>
## A08｜为什么 Agent 需要多次运行评测？（P0）


### 一次演示成功，可能只是碰巧走对了

同一道任务重复运行，模型可能选不同工具、不同步骤，也会遇到不同响应。一次完成不足以说明长期可靠。

应多次运行并统计成功、成本和失败类型，尤其观察涉及写入、恢复与复杂分支的任务。

**直答：** Agent 评测需要重复运行来估计行为稳定性；平均成功率之外，还要看任务级反复成功和严重错误。

### 进一步：公式、边界与追问

**技术表述：** 模型采样、工具时延、环境反馈和用户互动会让同一任务产生不同轨迹。

**展开：** 分别报单次成功率、重复成功可靠性、平均/尾部步数、恢复率、成本和 policy violation。固定模型后增加解码 seed，不冒充训练 seed。

**追问：一次成功的演示能证明什么？** 证明存在一条成功路径，不证明系统稳定。可用 pass^k 补充可靠性观察。

**易错：** 不要筛掉超时或失败样本后才计算成功率。依据：S31。

<a id="A09"></a>
## A09｜记忆与长上下文的本质差别是什么？（P0）


### 长上下文像摊开笔记，记忆像整理好的档案

长上下文把较多材料直接放在当前输入里；外部记忆可以长期保存、筛选、更新，再按需取回。

档案可能过期或记错，所以“记得更多”不自动更好。需要知道谁写入、来自哪里、什么时候应更新或删除。

**直答：** 两者分别扩展当前可见材料和跨任务持久信息；外部记忆还需要写入、检索、冲突与生命周期管理。

### 进一步：公式、边界与追问

**技术表述：** 长上下文容纳更多当前输入；记忆系统还要管理写入、更新、检索、冲突、删除和来源。

**展开：** 记忆可存在摘要、数据库、向量索引或参数中。业务规则要存实体、内容、版本、生效时间、来源和适用范围；用户偏好与系统规则不能混为一层。

**追问：新规则与旧规则冲突怎么办？** 根据权威与有效期判断替换、保留历史或请求澄清，不能一律“后写覆盖先写”。

**易错：** 记忆更长也可能保留过期错误。依据：S33。

<a id="A10"></a>
## A10｜选择性遗忘怎么测？（P1）


### 忘掉旧地址，又别把姓名一起删了

选择性遗忘要让某条不该再用的信息失效，同时保留其他仍有效内容。删除数据库一行后，还要检查摘要、缓存或其他副本是否会把旧信息带回来。

可以用应忘信息、应记信息和冲突信息分别测试。

**直答：** 遗忘评测同时验证目标信息不再被使用、相关正常信息仍保留，并检查不同存储层的残留。

### 进一步：公式、边界与追问

**技术表述：** 写入一批信息、更新或删除其中部分，再测应保留、应替换、应遗忘的内容是否分别正确。

**展开：** 不只从向量库删一行，还要检查摘要、缓存、备份恢复和相关派生记录；按系统设计明确删除范围。评测不要求模型忘掉通用常识，而是正确处理指定记忆。

**追问：回答“不知道”就算删除成功？** 还要确认旧事实不会通过别的路径再次被检索或使用。

**易错：** 记忆基准有不同版本和维度命名，引用时固定论文版本。依据：S33。

<a id="A11"></a>
## A11｜提示注入防御应该放在哪里？（P0）


### 不要让读到的一张纸，自动获得操作账户的权限

外部网页写着“执行这条命令”，并不等于用户要求这样做。防御要在内容来源、模型决策、工具授权和执行检查等位置共同建立边界。

即使模型一时受骗，工具也应拒绝越权操作，而不是把全部防线放在一句提示词上。

**直答：** 通过来源隔离、最小权限和执行校验限制外部内容的控制力，并用实际任务攻击验证多层防线。

### 进一步：公式、边界与追问

**技术表述：** 在不可信内容进入决策、工具执行和外部状态改变的多个环节建立约束。

**展开：** 文档和工具返回标注来源；检索权限前置；执行工具只接收明确结构参数；高风险动作校验当前用户目标；敏感数据读取和输出按业务权限检查。

**追问：模型能识别所有恶意指令吗？** 不应依赖完美识别；即使误判文本，执行层仍应限制越权行为。

**易错：** AgentDojo 风格评测同时看任务实用性和攻击成功，不只看拦截率。依据：S32。

<a id="A12"></a>
## A12｜多 Agent 什么时候值得用？（P1）


### 多人分工有收益，也有沟通成本

独立资料整理和交叉检查可以并行；但如果任务步骤紧密依赖，多个 Agent 反复解释和传递上下文，可能更慢、更贵，还会传播同一种错误。

比较时应与单 Agent 或固定流程使用相近预算，而不是仅看最后答案更长。

**直答：** 在任务可分、分工清楚且协调收益超过成本时使用多 Agent，并评估通信、重复工作和错误相关性。

### 进一步：公式、边界与追问

**技术表述：** 当任务可有效分解、存在互补信息或独立核查价值，且协调成本可控时。

**展开：** 明确角色输入输出、共享状态、冲突解决和停止规则；多个相同模型同提示可能共享错误，不能等同于独立专家投票。比较固定总 token/时长预算下的单 Agent 基线。

**追问：分工后分数升了说明什么？** 可能只是多用了采样与上下文，应做预算匹配和角色消融。

**易错：** Agent 数量是实现选择，不是能力指标。

<a id="A13"></a>
## A13｜上下文压缩如何避免丢失关键事实？（P0）


### 压缩会议纪要，不能删掉“仅限周五”这个条件

上下文压缩要缩短文字，但保留任务目标、约束、关键事实、未决事项和已经执行的动作。丢掉一个日期或否定词，后续决策就可能完全改变。

检验方法是让压缩前后完成同样任务，观察关键约束是否仍被满足。

**直答：** 以决策所需信息是否保留来评估压缩，不能只看压缩率或摘要是否通顺。

### 进一步：公式、边界与追问

**技术表述：** 将可核验事实、约束、待办与副作用状态结构化保存，原始证据保留可回溯引用。

**展开：** 摘要时区分已完成/计划/失败/未知；保留单位、日期、否定、来源和权限。压缩效果用后续任务成功率与事实恢复测，不只看字数减少。

**追问：反复摘要会怎样？** 误差可能逐轮累积；可采用分层记忆、固定关键字段和按需回读原始记录。

**易错：** 把工具报错总结成“已经处理”会污染后续决策。

<a id="A14"></a>
## A14｜LangGraph 项目应该拿出哪些证据？（P0）


### 用了框架，还要证明它解决了哪个实际麻烦

展示一个具体任务，从状态变化、工具调用到中断恢复和最终结果。让面试官看见为什么需要这些节点，而不是只画一张复杂流程图。

框架已有能力、你写的业务规则、你做的评测，应分别说清。

**直答：** 用真实任务记录、状态定义、失败恢复和对照评测证明项目价值，并准确划分个人贡献。

### 进一步：公式、边界与追问

**技术表述：** 状态图只是入口，还需任务集、节点日志、终态检查、故障恢复和版本对比。

**展开：** 每个任务记录目标、允许工具、证据库、策略约束、预期终态；注入超时、空结果、权限不足、规则更新和恶意工具内容。报告任务成功、无效调用、违规、恢复、步数与 p95 时延。

**追问：最有价值的新增实验是什么？** 固定任务集比较固定流程、单 Agent、加入恢复、加入记忆的增量效果，并做同预算对照。

**易错：** 没有真实运行时，表述为实验方案，不填虚构 N 类任务/M 类故障。
